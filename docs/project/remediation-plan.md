## Фаза 1 — Гігієна гілок і процесу (СТОП-кровотеча)

Спільна для A і B. Найвищий пріоритет: поки це не зроблено, кожна нова правка може повторити F6/F7.

### R-01 — Архівні теги перед будь-якими діями
- [ ] `git tag archive/master-2026-05-30 master` та `git tag archive/multitenant-2026-05-30 multitenant`, запушити теги.
- **Критерій успіху:** обидва теги існують на origin; жоден коміт не може загубитись.
- **Перевірка:** `git ls-remote --tags origin | grep archive/`.
- **Анти-критерій:** почали force-push/reset гілок без тегів.

### R-02 — master = єдиний канон, Zed і робота на ньому
- [ ] Зробити робочою основну теку на гілці master (або перенести роботу в `Smartest-prod-backport`, або переключити `C:/Python_projects/Smartest` на master) і **схлопнути до одного worktree**.
- **Критерій успіху:** `git worktree list` показує рівно один шлях; основна тека на `master`.
- **Перевірка:** `git worktree list` → 1 рядок; `git -C <основна тека> rev-parse --abbrev-ref HEAD` → `master`.
- **Анти-критерій:** лишились дві теки на різних гілках (F5 не усунуто) — головне джерело «в зеді не та гілка».

### R-03 — Прибити footgun деплою на ВСІХ гілках + branch-aware guard
- [ ] Прибрати хардкод `PROJECT_DIR` скрізь (на multitenant теж, поки вона існує). Додати в `deploy.cjs` перевірку: для `--target=prod` гілка checked-out має бути `master`, інакше `exit 1`.
- **Критерій успіху:** неможливо задеплоїти не-master код на prod; немає хардкоду абсолютного шляху.
- **Перевірка:** `git grep -n "PROJECT_DIR" -- deploy/deploy.cjs` на master і multitenant → жодного абсолютного хардкоду; ручний тест: `--target=prod` з не-master гілки падає з explicit-помилкою.
- **Анти-критерій:** `node deploy/deploy.cjs --target=prod` із multitenant-дерева заливає multitenant-код (повтор session 101).

### R-04 — Заморозити ручний backporting (процесне правило)
- [ ] Зафіксувати правило в `testing-protocol.md`: перенесення будь-якої фічі між гілками — **тільки окремим PR з прогоном `tests/acceptance/`**; copy-paste між worktree заборонено.
- **Критерій успіху:** правило записане; нові переноси йдуть через PR.
- **Перевірка:** розділ «Branch policy» присутній у `testing-protocol.md`.
- **Анти-критерій:** з'являється новий коміт із дублем тієї самої правки на двох гілках із різним хешем (як Gemini-timeout `afaf07d`/`da8d908`).

- **Анти-критерій:** stash-і просто залишені «на потім» (накопичення F11).

### R-06 — Почистити нумерацію девлогу

- **Перевірка:** `git diff master archive/multitenant-2026-05-30 --stat` показує лише свідомо-невзяте.
- **Анти-критерій:** multitenant далі «живе» паралельно й приймає коміти.

### Якщо B (cutover multitenant → prod)

- **Перевірка:** на проді є і `billing/`, і `_annotate_recent_rows`, і `search_gate_downgrade` одночасно.

## Фаза 3 — Де-франкенштейнізація коду (усуваємо симптоми)

Робиться **після** того, як лінія стала однією. Кожен пункт прив'язаний до конкретної скарги користувача.

### R-10 — 🧠 Пам'ять/геометрія: єдиний модуль формату + golden-тест
- [ ] Винести серіалізацію/парсинг геометрії (`[CHAT-TURN]`, `[Speaker]`, `[CORE]`, `[LONG-MEMO]`, `[NOW]`, поділ `\n\n`) в **один** модуль із типами. Усі інші місця користуються ним, не парсять руками.
- **Критерій успіху:** формат визначений в одному файлі; round-trip golden-тест (serialize→parse→serialize) стабільний; `trim_terminal_user_duplicate` і annotate спираються на спільний парсер.
- **Перевірка:** `git grep -l "CHAT-TURN\|\[Speaker:" -- '*.py'` → один модуль-власник (решта імпортують); новий тест `tests/acceptance/test_geometry_format_roundtrip.py` зелений.
- **Анти-критерій:** зміна формату в одному місці знов мовчки ламає інше (повтор session 111). Якщо для фіксу довелось правити формат у 2+ файлах — критерій НЕ виконано.
- **Поведінкова перевірка (smoke):** у груповому чаті двоє пишуть різні факти про себе → бот не змішує, не каже «двічі питаєш».

### R-11 — ⚠️ Розбити god-function на пайплайн
- [ ] Розділити `_process_message_inner` на явні шари (нормалізація події → planner → executors → final responder), як описано в `strategy.md`/`routing-contract.md`.
- **Критерій успіху:** жоден метод обробки повідомлення не перевищує ~80 рядків; кроки викликаються як окремі тестовані функції.
- **Перевірка:** wiring-тести (session 107) лишаються зеленими після рефактора; найбільша функція у `message_logic.py` < 80 рядків (можна перевірити скриптом).
- **Анти-критерій:** правка одного кроку (напр. медіа) валить несуміжний (напр. пошук) — ознака, що зв'язність не зменшилась.

### R-12 — 🧠 Семантична релевантність пам'яті
- [ ] Замінити `_score` (підрахунок підрядків, `manager.py`) на семантичний відбір long-term.
- **Критерій успіху:** на наборі прикладів «питання → який спогад має підтягнутись» правильний спогад у топі.
- **Перевірка:** новий тест із 5–10 кейсів релевантності проходить; старий substring-`_score` більше не єдине джерело ранжування.
- **Анти-критерій:** бот підтягує нерелевантний старий спогад на просте питання.

### R-13 — 🔎 Єдина консистентна архітектура відсікача пошуку
- [ ] Закріпити gate як **FILTER** (не promoter) у канонічній гілці; explicit-keyword перемагає reply_to_bot downgrade (session 109+115 — звести в один консистентний шлях).
- **Критерій успіху:** на chat-питання gate не викликається (0 токенів); на «гугли …» — пошук іде попри reply_to_bot.
- **Перевірка:** `tests/acceptance/test_search_gate.py` зелений; ручний smoke: «поясни принцип реактивного двигуна» → без пошуку; «гугли курс долара» → з пошуком.
- **Анти-критерій:** gate знов промотить chat→search на кожному повідомленні (зливає токени) АБО ковтає явні «гугли».

### R-14 — 🌐 Консолідація сайту/адмінки
- [ ] Привести до ладу те, що реально в prod: або довести мінімальну адмінку master до робочого вигляду (A), або довести multitenant-портал (B). Прибрати «стрибання кнопок» (єдиний CSS — вже частково в `app/static/admin.css`).
- **Критерій успіху:** усі сторінки, на які є посилання в навігації, відкриваються (нема 404/битих); один набір flash-стилів; один `.btn`.
- **Перевірка:** ручний прохід усіх роутів адмінки на проді → кожен віддає 200 і коректний HTML; `git grep -c "<style>" app/admin_ui.py` мінімізовано.
- **Анти-критерій:** частина пунктів меню веде в нікуди / «наполовину працює» (поточна скарга F2-наслідок).

### R-15 — In-process стан
- [ ] Задокументувати або винести стан, що губиться при рестарті / не шариться між процесами bot↔admin (`media/album_registry.py`, `MemoryManager._locks/_last_consolidation`).
- **Критерій успіху:** для кожного in-memory стану є свідоме рішення (ephemeral-ok / винести у сховище), зафіксоване в коді-коментарі або девлозі.
- **Перевірка:** code review; немає мовчазного припущення, що admin-процес бачить стан bot-процесу.
- **Анти-критерій:** функція покладається на спільний in-memory стан між двома процесами.

## Загальний Definition of Done (критерій успіху всієї реструктуризації)

Реструктуризацію вважаємо завершеною, коли **одночасно**:

1. **Одна канонічна гілка, одна робоча тека, branch-aware деплой.** `git worktree list` → 1; деплой на prod можливий лише з master; footgun усунуто. *(R-02..R-04)*
2. **Acceptance-гейт зелений на канонічній гілці** і ловить усі 4 класи скарг (геометрія, помилки, пошук, сайт) як окремі інваріанти. `pytest tests/acceptance/ -q` → 0 failed. *(R-10..R-14)*
3. **Чотири скарги відтворюються-та-закриваються** поведінково (smoke у Telegram):
   - геометрія: у групі бот не плутає, хто що сказав, і не каже «двічі питаєш»;
   - помилки: тегнули бота — він або відповідає, або явно каже «порожня відповідь», не мовчить;
   - пошук: теорія/lore → без гуглу; «гугли …» → гуглить; токени не зливаються;
   - сайт: усі пункти меню адмінки відкриваються.
4. **Немає паралельної гілки, що приймає коміти** (multitenant в архіві — A; або стала prod — B). *(R-09)*
5. **Девлог і нумерація чисті**, рішення A/B зафіксоване. *(R-00, R-06)*

> Орієнтир верхнього рівня — критерії успіху зі `strategy.md` (§ «Критерії Успіху»). Цей план — шлях до них без Франкенштейна.

## Ризики і відкат
